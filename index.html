El problema de escalar tienda por tienda

Una base de datos por cliente no aguanta miles.

Es la opción intuitiva al principio, y la que más se paga después: cada tienda nueva multiplica el trabajo operativo en vez de sumarlo.

DB por tienda

  • 2000 migraciones cuando cambia el esquema
  • 2000 backups, 2000 conexiones activas
  • Cada tienda nueva es una tarea de infraestructura
  • El costo de servidor crece linealmente con los clientes

Row-level tenancy

  • Un esquema, una migración, todas las tiendas al día
  • Un pool de conexiones para toda la plataforma
  • Alta de tienda nueva: un registro, no un deploy
  • El costo escala con el uso real, no con la cantidad de clientes
Cómo se garantiza el aislamiento

Tres capas, en el orden en que corren en cada request.

El riesgo real de compartir esquema es que un desarrollador se olvide del filtro y exponga datos de otra tienda. Estas capas hacen que ese error sea prácticamente imposible.

01

Se resuelve el tenant una sola vez

El TenantMiddleware lee el subdominio (o dominio propio) apenas entra el request y lo cuelga en req.tenantId antes de que llegue a cualquier controller.

02

Se inyecta donde se necesita

El decorator @CurrentTenant() lo pone a disposición de cualquier controller, sin pasarlo manualmente por cada capa de la app.

03

La base de datos lo exige

PrismaService.forTenant() fuerza el where: tenantId en todos los queries — el filtro no depende de que nadie se acuerde de escribirlo.
